The proof that adopt_core=true changes nothing a user sees. The same answers are rendered twice, adopt_core=false and adopt_core=true; every command of both generated CLIs runs with the same inputs and the outputs are compared byte for byte. This runs in this repo's own test suite, which the template gate runs first, so a template change that makes the two variants differ fails the gate.

## Acceptance

- Given the same answers rendered with adopt_core=false and adopt_core=true, When every command and group runs with --help, Then the outputs are identical and the help snapshots of the two projects are the same files [check: tests/test_output_parity.py]
- Given both projects, When commands run that succeed, fail with a standard error (not initialized, exit 4), fail with invalid arguments (exit 2) and hit an unexpected error, each with and without --json, Then stdout, stderr and the exit code are identical [check: tests/test_output_parity.py]
- Given both projects, When --version and describe --json run, Then the outputs are identical [check: tests/test_output_parity.py]
- Given cli_name sitemap-xml and package rb_sitemap_xml, When the same comparison runs, Then it is identical too [check: tests/test_output_parity.py]

## How to test

Integration: copier copy --vcs-ref HEAD of both variants into tmp_path, uv sync, run the installed console script by subprocess with a fixed environment (no colour, fixed width, empty HOME config). Compare per case. Slow test: mark it so the repo's quick runs can skip it, but the gate runs it. Red first: before CG-038 the adopt_core=true project still carries copies, so make the test also assert that it holds no copy.

## Basis

The template gate's variants in scripts/check_template.sh (copier copy, --vcs-ref HEAD, --trust, env without credentials) and the repo test style of tests/test_template_drift.py.

In Gitea CI the gate's `standard: commands` step is red for every package from the template (semkit, dataio): "`<cli>` lists no commands (no Commands heading in its output)". On the Mac it is green. The cause: the gate runs the installed console script with the runner's environment; Gitea Actions sets GITHUB_ACTIONS=true, Typer reads it (and FORCE_COLOR, PY_COLORS) at import and forces terminal output, so even in a pipe the bare `<cli>` prints ANSI codes and the heading does not match.

The fix is in the gate, so every package is fixed by the new gate tag with no change of its own: every probe of the package's installed CLI (the `standard: *` steps and the wheel smoke run) runs with GITHUB_ACTIONS, FORCE_COLOR and PY_COLORS removed from its environment. The pytest step keeps the CI variables it gets (it checks the package's tests as CI runs them). Nothing else in the environment changes.

## Acceptance

- Given a package from the template, When rb-release check runs with GITHUB_ACTIONS=true FORCE_COLOR=1 PY_COLORS=1 in its environment, Then the `standard: commands` step and the other `standard: *` steps pass as they do without those variables [check: gate/tests/test_release.py]
- Given a package whose bare command lists no commands, When rb-release check runs with or without GITHUB_ACTIONS=true, Then `standard: commands` fails with the same message as today [check: gate/tests/test_release.py]
- Given the template gate, When it runs every variant, Then it passes [check: sh scripts/check_template.sh]

## How to test

Integration test in the gate's test file over a generated or fixture package, run once with the CI variables set in the test process environment; the probe output must reach the parser without ANSI codes.

## Basis

The gate has one place that runs the package's commands: put the environment there, once, as a named set of the three variables shared with the pytest step's set. Keep step names and messages unchanged.

## Problem

Both holes were found by the mcp architect while wiring the CLI family into one MCP server. x-rb-skills[] carries name and description but no path, so the skill text needs another process. And nothing states that family membership is the DISTRIBUTION name rb-*: a consumer that filters by the entrypoint prefix loses rb-llmkit (llm), rb-wordpress-bulk-editor (wp-bulk) and rb-mediagen (mediagen) — the inventory I gave mcp was short by those three for exactly that reason.

## Goal

A consumer of describe --json (rb-mcp, clidocs, Windmill) reads the skill text without a second process, and knows family membership from the distribution name instead of guessing it from a binary name.

## Acceptance (Given–When–Then)

- Given an installed package with the skill part on, when its describe --json is read, then each x-rb-skills[] entry carries the filesystem path of the bundled skill directory, and the package skill text is readable from it with no other call
- Given the Standard, when a consumer reads where family membership is defined, then it says the distribution name rb-* and that the tool's own name is x-rb-tool.tool

## Implementation decisions

- path is the bundled skill directory inside the installed distribution, not the install target: the target depends on the consumer's tool and scope.
- The Standard states family membership once, in Technology, next to the three names.

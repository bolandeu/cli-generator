semkit's `read` is a Click chain=True group with 145 steps: a step is part of one pipeline, and --json is the root's global option (`semkit --json read IN STEP ...`). The gate's json and errors rules look for --json only in each command's own help and probe `<cli> <command> --json <unknown option>`, so all 145 steps fail although `semkit --json read IN STEP --bogus` prints the INVALID_ARGUMENTS envelope with exit 2. The Standard already says --json works anywhere before `--`. Make the rules accept the global form: a command takes --json when its own help or the root's help lists it, and the errors probe puts --json first (`<cli> --json <command path> <unknown option>`). No detection of chained groups, no exception keys. The Standard's Output rule says the same in one line.

## Acceptance

- Given a CLI whose root help lists --json and whose command help does not, When the gate runs, Then 'standard: json' passes [check: gate/standard/tests/test_standard.py]
- Given a CLI where neither the root help nor a command's help lists --json, When the gate runs, Then 'standard: json' fails and names that command [check: gate/standard/tests/test_standard.py]
- Given a CLI that answers '<cli> --json <command> --unknown' with the INVALID_ARGUMENTS envelope and exit 2 but rejects a local --json after the command, When the gate runs, Then 'standard: errors' passes [check: gate/standard/tests/test_standard.py]
- Given a package generated from the template, When the template gate runs, Then every variant still passes [check: sh scripts/check_template.sh]

## How to test

Unit level through the existing fake-CLI fixtures of the gate's standard tests: one fake CLI with --json only on the root, one with --json nowhere. Red first.

## Basis

Follow check_json and check_errors as they are; reuse Package.bare for the root help. The Standard's Output section, rule 'standard: json'.

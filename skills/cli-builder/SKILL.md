# CLI Builder

This skill produces every CLI tool under one architecture, so that a year from
now any of them can be opened by a coding agent and understood without
re-deriving conventions. It has two modes. Pick one before doing anything else.

- **Scaffold** — no working CLI exists yet, or the existing one is being fully
  replaced.
- **Refactor** — a CLI or script already exists and should be brought onto
  this architecture while preserving its behavior and history.
- **Update** — the CLI was generated by this template (it has a
  `.copier-answers.yml`) and should pick up a newer template release.
  Check for that file first: a project that has it is never refactored
  by hand, it's updated.

Read `reference/architecture.md` once per session before generating or
judging any code — it is the contract every generated package must satisfy.
`reference/conventions.md` has the exact JSON envelope, error codes and exit
codes to reuse verbatim (do not invent new ones per project).

Architecture governs the package's *shape*. The code you actually write
inside it (`core/services.py`, a `providers/` integration, a migrated
function) is governed by these four rules instead
(adapted from the MIT-licensed [karpathy-guidelines](https://github.com/multica-ai/andrej-karpathy-skills)):

1. **Think before coding.** State assumptions; if multiple interpretations
   exist, present them instead of picking silently; push back if the task
   implies more than it needs.
2. **Simplicity first.** Minimum code that solves the task — no commands,
   providers, or config fields beyond what was asked; no abstractions for
   single-use code; no error handling for scenarios that can't happen.
3. **Surgical changes** (Refactor mode especially). Touch only what the
   checklist item or request requires — don't reformat, "improve," or
   refactor adjacent code you weren't asked to touch.
4. **Goal-driven execution, test first.** Turn the task into a verifiable
   check rather than looping on "make it work" — this is why every mode
   below ends in `uv sync && pytest && doctor`. TDD is required and
   checked (`~/Work/dev/docs/testing.md`): the failing test is committed
   before the code, and its red run goes into the readiness report; an
   existing test is never edited to fit the code — `release.py --check`
   lists every test changed or gone since the last tag (`existing tests`),
   and each goes into the report with its reason; acceptance scenarios
   come from dev with the user, contract tests from the consumer — you
   write the unit tests and pass theirs; mutation testing
   (`uv run --group mutation mutmut run`) now and then, outside the gate.

## Mode: Scaffold

1. Clarify with the user (or infer from the task) before generating:
   Three names, deliberately separate (standard §10):
   - `package_name` — the Python import package; for a new tool
     `rb_<slug>` (`rb_serp`). Also the keychain service, env var prefix and
     `.<package>/` project dir.
   - `cli_name` — the command users type; default `<slug>` (`package_name`
     without `rb_`, `_` → `-`: `serp`). Runtime code reads it from the
     installed console script (`core.version.cli_name()`), never from
     `__name__`.
   - `dist_name` — the distribution (`[project] name`, what `uv tool
     install/upgrade` and other tools' dependencies use); default
     `rb-<slug>` (`rb-serp`). Generic names collide with other people's
     PyPI packages. Runtime code gets it from `_distribution.DIST_NAME`.
   - `project_name`, one-line `description`, `author_name`.
   - Whether it needs credentials (`include_auth`) — default yes if the task
     mentions any external API/provider. Only without credentials:
     `include_providers=false` drops `providers/` for a CLI that calls no
     external service.
   - `repository_url` — the Gitea repo URL this will live at. Decide it
     **now**, before generating, even though the repo itself is only
     created in the Publish step below: default to
     `https://homeserver.tailee01ab.ts.net:3000/bolandeu/<repo>` with `<repo>` = `package_name`
     with `_` → `-`, unless the user names something else. Passing
     it to copier is what puts the real `uv tool install "git+…"` command
     into README.md, the bundled SKILL.md and `.copier-answers.yml` from
     the start instead of an `<owner>/<repo>` placeholder to chase later.
   - The install answers (`[tool.rb.install]`, `reference/architecture.md` §1):
     `install_homeserver_users` (comma-separated homeserver users, blank =
     build and publish only) and `install_mac` (bool). Default: homeserver
     user `rbtools` + Mac. A library: publish only
     (`--data install_homeserver_users= --data install_mac=false`).
   - What `run` should actually do — this is the one piece of real business
     logic the template does not provide.
2. Generate the skeleton with copier from **`https://homeserver.tailee01ab.ts.net:3000/bolandeu/cli-generator.git`** —
   the single template source (keep the `.git` suffix: without it copier
   takes the URL for a local path): it becomes `_src_path` in the project's
   `.copier-answers.yml`, so every later `copier update` pulls released
   tags from Gitea on any machine (never a local path or the
   `~/.claude/skills/cli-generator` symlink). Its `copier.yml` has
   `_subdirectory: template`, so no `--subdirectory` flag is needed:

   ```bash
   uvx copier copy https://homeserver.tailee01ab.ts.net:3000/bolandeu/cli-generator.git <dest-dir> --trust \
     --data package_name=<name> --data project_name="<Name>" \
     --data description="<one line>" --data author_name="<name>" \
     --data cli_name=<command> --data dist_name=rb-<slug> --data include_auth=true \
     --data repository_url=https://homeserver.tailee01ab.ts.net:3000/bolandeu/<repo>
   ```

   Copier picks the latest release tag; `--vcs-ref vX.Y.Z` pins one. A
   local checkout of this repo as the source is only for testing a
   template change before it is released (see this repo's AGENTS.md). An
   existing project with another `_src_path` switches by editing that one
   line to `_src_path: https://homeserver.tailee01ab.ts.net:3000/bolandeu/cli-generator.git` (commit
   `chore(copier): template source https://homeserver.tailee01ab.ts.net:3000/bolandeu/cli-generator.git`), then
   `uvx copier update --trust --defaults --pretend` must say "Updating to
   template version …".
3. Implement the real logic:
   - Business logic goes in `src/<package_name>/core/services.py` (or new
     modules under `core/`), never inside `commands/*.py`. Commands stay
     thin: parse args → call a service → call `output.emit_success` /
     `output.guard`.
   - External integrations go under `providers/`, one module per service,
     subclassing `providers.HttpProvider` — it already maps 401/403,
     429/5xx, timeouts and network errors onto the CLI's error codes and
     retries what's safe; don't re-implement that per project. The
     credential comes from `credentials.manager` inside `auth_headers()`.
     Each provider declares `credential_fields` and `required`, and
     implements `health_check()` — one cheap read-only call (the test
     suite fails without it); that is what `auth status --check`
     reports in the cross-tool shape (`architecture.md` §4). One
     credential per site/host/account → `per_target = True`, read it
     under `self.credential_name`.
   - Running any program `uv` can't install (`ffmpeg`, `git`, `npx`,
     another CLI)? Declare it in `pyproject.toml` `[[tool.rb.external]]`
     (name, required, min_version, check, why) — the gate fails on an
     undeclared or unused one — and reach it through `core.deps.require_cli`.
   - Keeps data (journal, results, history, a cache of paid responses)?
     `--data include_db=true`: shared PostgreSQL from `<TOOL>_DATABASE_URL`,
     else local SQLite; tables in `core/tables.py` + a hand-written Alembic
     migration; other tools read only `<tool>_v1_*` views; cross-tool keys
     from `core/normalize.py` (`architecture.md` §12). Dev SQLite → prod
     PostgreSQL for append-only tables: mark them `info={"push": ...}` and
     use `db push`.
   - An integration that doesn't speak HTTP: `--data include_http_provider=false`
     drops `providers/http.py` and the `httpx` dependency; subclass
     `providers.Provider` directly.
   - Calling another of our CLIs as a subprocess? Get its path with
     `core.deps.require_cli("<cli>", "<min version>", install_url="<its repo URL>")` first — it fails
     with `DEPENDENCY_TOO_OLD` instead of a confusing downstream error.
   - Wire the real work into `commands/run.py`, replacing the placeholder.
   - Any new command group (`<cli> thing list|add`) is created with
     `output.group("...")`, never `typer.Typer(...)`, so a bare
     `<cli> thing` prints help instead of a usage error.
   - Do not edit `CHANGELOG.md` and do not add changelog fragments:
     `antagor publish` writes the changelog from the titles of the
     tickets it publishes. Put the user-visible meaning of a change into
     the ticket title (`reference/architecture.md` §8).
   - Depending on another of our tools? A version range in `dependencies`
     (`"rb-serp>=0.3"`) and `rb-serp = { index = "gitea" }` in
     `[tool.uv.sources]` — never a git `tag =`, `branch = "main"` or a
     committed `path =`; `architecture.md` §8, "Depending on another tool".
   - A key one CLI shares with others (Google service account, S3, Telegram,
     GitHub)? The provider reads the shared name through `legacy_env`
     (`architecture.md` §4). A new key goes to sysadmin as a ticket
     (`docs/contracts/sysadmin.md`, "Ключи").
4. Verify before calling it done — the whole gate is one command, the
   same one every release and CI run (`architecture.md` §8):
   ```bash
   cd <dest-dir> && uv sync && uv run scripts/release.py --check && uv run <package_name> doctor
   ```
   It runs `uv lock --check`, ruff check + format, ty, pytest (coverage
   floor, help contract + snapshots, `auth status` shape, `docs` document), and builds + installs the wheel into a throwaway venv
   to run `<cli> --version`/`--help`; the first failing step is named with
   its output. `uv sync` writes `uv.lock` — it's committed. **Run
   `release.py --check` before every commit**, not only at the end.
   Under Antagor the same gate runs as the ticket's `checks`
   (`.agents/antagor/antagor.toml`, with
   `scripts/check_command_docstrings.py`).
5. Publish — follow "Publish" below. Scaffolding is local
   until the user says otherwise: nothing leaves the machine before the
   user's yes (that section, step 2).

## Mode: Refactor

Never rewrite blind. Work through `reference/refactor-checklist.md` in the
order it's written — later items assume earlier ones are already true (e.g.
you can't add `--json` output cleanly before commands are split from
business logic).

0. **Work on a branch, not on main.** This touches most files in the repo
   across several checklist items. Before changing anything: run `git
   status` (stash or ask about anything uncommitted first — never start a
   refactor on top of someone else's in-progress work), then create a
   feature branch (`git checkout -b cli-architecture-refactor` or similar)
   unless the user says otherwise or is already on one. This is what makes
   the refactor reviewable as one diff and trivially abandonable if it goes
   sideways — do not skip it even for a "quick" refactor.
1. **Audit first.** Read the existing package and check it against every
   item in the checklist. Report gaps before changing anything (a short
   list: what's missing, what's already fine — don't redo what's already
   compliant).
2. **Decide the migration strategy** based on the audit:
   - If the project already has significant structure worth keeping
     (its own tests, git history, real logic scattered through files):
     migrate in place, checklist item by item, smallest safe commits.
     Generate the reference skeleton into a scratch directory (same copier
     command as Scaffold mode, into a `/tmp` or scratchpad path) purely as a
     structural reference to copy specific files from (`core/errors.py`,
     `output/`, `credentials/manager.py` rarely need project-specific
     changes — copy them near-verbatim) — do not overwrite the target
     directory with it. `scripts/`, `.agents/antagor/antagor.toml`
     and `tests/test_help.py` (the --help contract) rarely need
     project-specific changes either — copy them near-verbatim, run
     `antagor init --prefix <PREFIX> --name <cli_name>` once in the target
     repo (it installs the git hooks; the prefix is 2–4 capital letters,
     the `antagor_prefix` answer), then
     `uv run pytest --snapshot-update` to create the help snapshots.
   - If the existing code is a small/ad-hoc script with little worth
     preserving beyond its core logic: scaffold fresh (Scaffold mode) into
     a new directory, then port the actual logic into
     `core/services.py` and `providers/`.
3. Preserve behavior: whatever the script/CLI did before must still work
   after, just reachable through the new command surface and passing
   through `output.emit_success`/`output.guard` instead of raw prints.
4. Secrets found hardcoded, in `.env`, or in committed config **must** move
   to `credentials/manager.py` (keyring + env var fallback) — flag this
   explicitly to the user, it's a real security fix, not just style.
5. Verify the same way as Scaffold mode (`uv sync && pytest && doctor`; the
   help test also checks `docs`), plus
   confirm any behavior that existed before the refactor still produces the
   same result.
6. Publish — follow "Publish" below (checklist item 12). A
   refactored script usually has never been `uv tool install`-able from
   anywhere; leaving it that way means the "works on any machine" half of
   the architecture is still missing after all the other items pass.

## Mode: Update

For a project with `.copier-answers.yml` (`_src_path` points at this
template, `_commit` is the template release it was last synced to):

1. `git status` must be clean — `copier update` refuses otherwise. Commit
   or stash, never delete.
2. `uvx copier update --trust` (add `--defaults` to keep every previous
   answer without prompting). A project from before template v1.2.1 has
   no `cli_name` answer: its default is `package_name` with `_` → `-`,
   which renames the command of a package with `_` in its name — pass
   `--data cli_name=<the command it has today>` (see `[project.scripts]`)
   unless renaming is intended. Before template v1.2.3 there is no
   `dist_name` answer either: the default `rb-<slug>` **renames the
   distribution** — see "Renaming the distribution" below; to keep the old
   name pass `--data dist_name=<current [project] name>`. `README.md` is
   never touched by an update (`_skip_if_exists`): it belongs to the
   project once generated. It three-way-merges the template diff since
   `_commit` with the project's own changes; business logic in
   `core/services.py`, `providers/`, extra commands and tests survive
   untouched. Conflicts land as `*.rej` files (or inline conflict markers)
   — resolve **hunk by hunk**, keeping the project's commands, providers
   and settings and taking the template's structural changes. Never
   resolve by taking one side wholesale (`git checkout --theirs/--ours`,
   copying the template file over): that silently deletes the project's
   own commands or the template's fixes. Delete each `.rej` afterwards and
   check `git diff` reads as intended before the gate. The update brings
   `[tool.rb.install]` into `pyproject.toml`; the gate now refuses a
   project without it. Check the answers: a library gets `homeserver = []`
   and `mac = false` (`reference/architecture.md` §1).
3. Run the full verify loop (Scaffold step 4). Read the diff: a template
   release can add a gate (coverage floor, a lint rule) that the
   project's existing code now fails — fix the code, don't lower the
   gate. A template release that changes a command's help (e.g. new
   `auth status` options) fails the help snapshots: run
   `uv run pytest --snapshot-update` and read the diff. Make the update its own ticket, titled
   `Template vX.Y.Z: ...` — that title becomes the changelog line.
4. **Crossing template v1.1.0** (the release standard: version from the
   git tag). Before `copier update`: if the
   project's current `version = "X.Y.Z"` has no tag, tag the current
   `main` commit with it (`git tag -a vX.Y.Z -m vX.Y.Z <sha>`) — otherwise
   the next build reports `0.0.0`. During the merge: `pyproject.toml`
   drops `version =` for `dynamic = ["version"]`; a hand-edited
   `scripts/release.py` is replaced by the template's verbatim. The
   changelog and the hooks move in step 5. After:
   `uv lock`, `uv run pytest --snapshot-update` once
   (help snapshots are only rendered on `copier copy`) and read the
   generated `tests/snapshots/help/` — fix any command the new
   `test_help.py` contract flags (missing `Example:` line or `help=`),
   implement `health_check()` on every existing provider (plus
   `credential_fields`/`required`) — `test_providers.py` names the ones
   missing it. `auth status` now emits the §8 report instead of
   `{"provider", "authenticated"}`: a breaking change for the CLI's own
   callers, so release it as a breaking bump (minor at `0.x`) in a
   ticket titled as a breaking change. Then the
   full verify loop. Releasing it is the Publish step below.
5. **Crossing the Antagor template** (release by `antagor publish`, no
   towncrier, no hand-made hooks). Use it for a project with its own old
   release: towncrier and fragments, `.githooks/`, `scripts/release.py
   patch|minor|major`, and a pre-push hook that pushes and notifies.
   Move it in this order:
   1. Hooks. Delete `.githooks/`, `scripts/install_hooks.sh`, the
      `.claude/settings.json` hooks and `herdr_name` files, and run
      `git config --unset core.hooksPath`. Then run `antagor hooks install`
      (it installs Antagor's pre-commit, post-commit and pre-push hooks and
      refuses while `core.hooksPath` is set).
   2. Towncrier and the old release command. Remove `towncrier` from
      `pyproject.toml` (the `[tool.towncrier]` table and the dev
      dependency), delete `changelog.d/` and the
      `<!-- towncrier release notes start -->` marker. Keep the released
      sections of `CHANGELOG.md`: Antagor adds new sections above them.
      Delete a `## [Unreleased]` heading. If the package has **never been
      released** (no `v*` tag), rename it to `## [X.Y.Z] - <date>`
      instead, because its first tag already contains those changes. Remove
      the `patch|minor|major` modes from `scripts/release.py`; keep only
      `--check` (the template's `release.py` is verbatim: take it).
   3. Deploy. Take `scripts/deploy.sh` from the template. It does the same
      as the old pre-push hook: push `main` with tags. Do not keep that
      logic in a hook.
   4. Antagor config. Take `.agents/antagor/antagor.toml` from the template
      (`copier update` brings it, with `scripts/deploy.sh` and
      `scripts/release.py`). Check `prefix` and `name`; the project may not
      have the `antagor_prefix` answer yet, so pass
      `--data antagor_prefix=<PREFIX>`. In `[publish]` set
      `versioning = "semver"`, `changelog = "CHANGELOG.md"` and
      `deploy_command = "sh scripts/deploy.sh"`.
   5. Checks. Set `checks = ["python3 scripts/check_command_docstrings.py",
      "uv run scripts/release.py --check"]`: the command docstring check
      and `release.py --check`. Then run `uv lock` and the gate.
   6. From now on every change is a ticket and a release is
      `antagor publish --bump patch|minor|major` (Publish step 6).
6. **Crossing template v1.2.6** (credential namespace = command name).
   Keychain service and env vars moved from the package name to
   `cli_name` (`rb_serp` → `serp`: `SERP_XMLRIVER_API_KEY`). If the two
   differ and the project didn't already override this, credentials stored
   under the old package namespace aren't found any more: either set
   `shared_namespaces = ("<old package name>",)` on the affected providers
   for a transition, or re-run `<cli> auth login` and rename env vars. If
   the project had patched `credentials/manager.py`/`health.py` to do this
   by hand, take the template's version (hunk by hunk) and drop the patch —
   `shared_namespaces`, `legacy_env` and `legacy_env_first` cover the usual
   reasons for those forks.
7. **Crossing template v1.2.9.** The gate gains an "external
   dependencies" step: declare in `[[tool.rb.external]]` every program the
   code runs (the step names each one) — including other CLIs called via
   `require_cli`, whose `min_version` can then move into the registry.
   `providers/http.py` is optional now: a project whose providers don't use
   `HttpProvider` updates with `--data include_http_provider=false` (and
   drops `httpx`); one that imports `providers.HttpProvider` keeps working
   (lazy export) but new code imports `from .http import HttpProvider`.
8. **Crossing template v1.5.0** (`describe --json`, OpenCLI). After the
   update `uv run pytest --snapshot-update` renders
   `tests/snapshots/describe.json` — read it: it is the contract the tools
   catalog publishes. With `include_db`: give every table in `tables.py`
   `info={"kind": "data" | "cache"}` (ask the user when it isn't obvious),
   declare every existing `<tool>_v1_*` view in `tables.views` with the
   columns its migration creates (types, `comment=` descriptions) — the
   test names any view missing or differing; files in the user data dir
   besides the SQLite file go in `core/data_files.py` `DATA_FILES`. A
   tool's own `CliError` with an exit code outside `EXIT_CODES` fails
   `test_every_exit_code_is_documented`: use a standard code. From v1.5.6
   (TDD): `uv lock` (new `mutation` dependency group), and the gate gains
   an `existing tests` step that only reports — from then on every report
   carries the red run and the changed existing tests with reasons.
9. **Crossing template v1.6.0** (kind="cache" → PostgreSQL schema
   `cache`, T30). `copier update` no longer touches
   `migrations/versions/` — they're the tool's history. With `include_db`:
   the template's example `<tool>_responses` table and `v1_responses` view
   arrive in `tables.py`/`tests/test_db.py` — delete them (and the tests
   that use them) unless the tool has that table. Give every cache table
   `schema=tables.CACHE_SCHEMA`, then write the move migration from the
   template's `migrations/versions/0002_cache_schema.py.jinja` (in
   cli-generator — update doesn't copy it): `ALTER TABLE public.<t> SET
   SCHEMA cache` per table, no-op on SQLite. Run `scripts/pg_test.sh`: the
   T30 tests (move keeps rows and dates, view still works, previous release
   gets CLI_TOO_OLD, push lands in `cache.<t>`, missing schema or rights
   is a clear error) must pass. Schema `cache` and the role's USAGE +
   CREATE on it in production are the infrastructure's — ask the user (sysadmin sets it up) before the release that moves anything.
10. **Crossing template v1.7.0** (consumer contracts, `architecture.md`
   §13). `uv lock` (pyyaml joins the dev group); `release.py` is verbatim
   and gains the `contracts` step. `tests/contracts/tools-catalog/<cli>.yaml`
   and `tests/contracts/fixtures.yaml` come with the update; consumers'
   contracts arrive through dev — never write or edit them yourself. Their
   `run` cases need this tool's offline data: fill `fixtures.yaml`
   (`placeholders`, `offline_cache`/`no_cache` fixtures in
   `tests/conftest.py`) — runs have no network and no real keys.
11. **Changing `include_auth` / `include_providers`** (`--data
   include_auth=false`): copier deletes the files the new answers no longer
   generate (`credentials/`, `commands/login.py`, `tests/test_auth.py`;
   `providers/`, `tests/test_providers.py`) — **except files the project
   edited**, which it keeps. After the update run `git status` and delete
   such leftovers by hand, plus the help snapshots of commands that are
   gone (`tests/snapshots/help/auth-login.txt`, `auth-logout.txt` —
   `test_no_orphan_help_snapshots` names them), then the gate. A `credentials/` dir left holding
   only `__pycache__` is harmless (the CLI looks for
   `credentials/manager.py`, not the directory). A CLI without
   credentials that doesn't use `providers/` answers
   `include_providers=false` instead of deleting `providers/` — deleted
   template files come back on the next update.
11. If `_commit` is a bare commit hash rather than a tag, the project was
   generated before the template had releases; `copier update` still
   works from that commit and moves `_commit` to the latest tag.
12. **Crossing the template release with `docs`** (`<cli> docs`, help
   standard: `reference/help-standard.md`). After the update run the help
   test (`uv run pytest tests/test_help.py`): it prints the command paths
   whose docstring does not meet the standard. Paste them into
   `tests/help_allowlist.txt` (the file is the project's; `copier update`
   never overwrites it), so the gate passes. Then empty the list over
   time: bring one docstring at a time to the standard, delete its line.
   New commands may not be added to the list.

13. **Crossing the sysadmin contract** (`docs/contracts/sysadmin.md`: Gitea
   source, Gitea Actions CI, secret scan, registry dependencies). Use it
   for a package on template v1.20.0 or older. The update runs without
   questions and without keys.
   1. Clean tree: `git status` shows nothing. Then switch the template
      source: in `.copier-answers.yml` set `_src_path:
      https://homeserver.tailee01ab.ts.net:3000/bolandeu/cli-generator.git` and
      `repository_url:` to the package's Gitea URL
      (`https://homeserver.tailee01ab.ts.net:3000/bolandeu/<repo>`). Commit
      `chore(copier): template source Gitea`.
   2. Check the source: `uvx copier update --trust --defaults --pretend`
      must say "Updating to template version …". Then run
      `uvx copier update --trust --defaults` and resolve conflicts hunk by
      hunk (step 2 above). The update brings `.gitea/workflows/ci.yml`,
      the `.gitignore` lines, `[[tool.uv.index]]` and the new gate.
   3. CI move. Gitea Actions runs only `.gitea/workflows/`. Delete the old
      workflow: `git rm -r .github/workflows` (and `.github/` if nothing
      else is in it). A workflow of the project's own that still matters
      is ported to `.gitea/workflows/` by hand. `tests/test_ci.py` fails
      while `.github/` exists.
   4. Secret scan. Install the scanner once: `brew install gitleaks`. The
      gate now runs it over the whole git history, with the template's
      root `.gitleaks.toml` (it allows the template's own fake test values
      from `tests/test_auth.py`). A fake test value of the package's own:
      add it to that file's `regexes` as one exact string
      (`'''^<value>$'''`), never a path or a rule disable. Any other
      finding is a leaked key: do not commit, do not rewrite history. Tell
      the Human the secret's name and file — revoking it at the provider
      is the Human's (contract, "Ключи", rule 5).
   5. `.env` in `.gitignore`. The update brings `.env` and `.env.*`; check
      with `grep -n '^\.env' .gitignore`. A tracked env file:
      `git rm --cached <file>`, and treat its values as leaked (step 4).
   6. Dependencies on our packages. In `pyproject.toml` replace
      `rb-x = { git = "…", tag = "vX.Y.Z" }` in `[tool.uv.sources]` with
      `rb-x = { index = "gitea" }`, and `"rb-x>=X.Y"` stays in
      `dependencies`. Then `uv lock`. The gate installs these packages as
      locked, from the `gitea` index only.
   7. Shared keys. A key several CLIs share has one Doppler name without a
      CLI prefix (`GOOGLE_OAUTH_SERVICE_ACCOUNT_JSON`). In the provider
      declare it as the fallback:
      `legacy_env: ClassVar[dict[str, str]] = {"api_key": "<SHARED_NAME>"}`
      (`architecture.md` §4). Remove any jq-style renaming from wrappers.
   8. New keys. For every env name `<CLI>_<PROVIDER>_<FIELD>` the package
      reads that is not yet in Doppler `tools/prd`, write a ticket for
      sysadmin: env name, where to get the value, who needs it. Give it to
      the Human to send. The value never goes into the repo, a file or the
      ticket.
   9. Gate and release. Run `uv lock`, `uv run pytest --snapshot-update`
      (read the diff), then `uv run scripts/release.py --check`. Ticket
      title: `Template vX.Y.Z: Gitea CI, secret scan, registry dependencies`.

### Renaming the distribution (standard §10: `rb-<slug>`)

The command (`cli_name`) and the import package don't change; only
`[project] name` does. For an existing package:

1. `uvx copier update --trust --defaults --data dist_name=rb-<slug>
   --data dist_name_legacy=<old name>` (or edit `[project] name` by hand in
   a non-template repo), then `uv lock`. `src/<package>/_distribution.py`
   must carry the same name — `tests/test_cli.py` fails otherwise.
   `DIST_NAME_LEGACY` makes an install still registered under the old name
   report its real version instead of `0.0.0`/none until it is
   reinstalled (standard §10); clear it (`--data dist_name_legacy=`) in a
   later release once every machine has the new name.
2. It is a **breaking change** for consumers: breaking bump (minor at
   `0.x`) in a ticket whose title names the old and new names.
3. Every consumer, in the same wave: rename the dependency and its
   `[tool.uv.sources]` key (`"yandex-oauth>=0.2,<0.3"` →
   `"rb-yandex-oauth>=0.3,<0.4"`, `rb-yandex-oauth = { index = "gitea" }`),
   `uv lock`, gate, release.
4. Machines: no uninstall step. Sysadmin's tool-updater follows the new
   name. Put the old and the new name in the ticket title, so it reaches the changelog.

## Publish (both modes)

The primary store is Gitea:
`https://homeserver.tailee01ab.ts.net:3000/bolandeu/<name>`. Nobody pushes
to GitHub — never run `gh repo create` or a push to a GitHub remote.
`[tool.rb.install]` in `pyproject.toml` decides who installs the package
(`reference/architecture.md` §1): sysadmin's tool-updater builds every tag
and a Mac agent keeps the Mac current. This skill sends no message to
sysadmin. Installability is proven by `release.py --check` (the built wheel
in a throwaway venv), which is part of the verify loop.

Do this after the verify step. Always *offer* publishing; don't leave the
package sitting unreleased without asking.

1. **Prepare the local repo.** If the directory isn't a git repo yet
   (Scaffold mode): `git init -b main && git add -A && git commit -m
   "Initial commit"`, then tag it — the version comes from the tag, and
   `antagor publish` needs one to bump from: `git tag -a v0.1.0 -m v0.1.0`.
   A scaffolded project already has `.agents/antagor/` from the template:
   run `antagor hooks install`. A refactored project without it gets
   `antagor init` in the Refactor step above, which installs the hooks too.
   In Refactor mode you're on a feature branch; merging it is the user's
   call. Fill in the repo URL now (step 4) so the first push already
   carries it.
2. **Push to Gitea.** The first push on repo init is allowed without
   asking (Human, 2026-10-18):
   ```bash
   git remote add origin https://homeserver.tailee01ab.ts.net:3000/bolandeu/<name>.git
   git push -u origin main --follow-tags
   ```
   `<name>` is the repo name decided in Scaffold step 1 / the refactored
   project's existing name. The first push creates the repo (push-to-create
   in the `bolandeu` org; outside it Gitea refuses with 403). Within about
   5 minutes sysadmin's repo-sync creates the private GitHub copy
   `bolandeu/<name>` with a push mirror. Nothing waits for it.
   A new tool going into service needs the user's yes **before** its repo
   exists. If the user declines, say that the placeholder in README.md and
   `src/<package_name>/data/SKILL.md` needs filling once a repo exists —
   don't silently leave it.
3. **Install once on the Mac**, for instant use (the Mac agent of
   sysadmin takes over upgrades). Skip it when `install_mac` is false.
   After the first tag is pushed:
   ```bash
   uv tool install --index gitea=https://homeserver.tailee01ab.ts.net:3000/api/packages/bolandeu/pypi/simple <dist_name> && <cli_name> --version
   ```
   It must print `0.1.0`. If the registry has no wheel yet (the tool-updater
   builds the tag within minutes), retry later; do not install the checkout
   (`uv tool install .`) and do not use the mirror instead. No message to
   sysadmin.
4. **Make sure the package knows its own URL** (the Gitea repo URL). In
   Scaffold mode with `repository_url` passed to copier this is already
   true. Otherwise replace the `<owner>/<repo>` placeholder in README.md
   ("Install") and `src/<package_name>/data/SKILL.md` ("Installation"), and
   for a copier-generated project also set `repository_url` in
   `.copier-answers.yml` — that file is the answer store `copier update`
   reads, so without this the next update would render the placeholder
   back. Commit these edits before the push.
5. **CI.** CI is Gitea Actions: `.gitea/workflows/ci.yml` from the
   template (`architecture.md` §8). It only repeats `release.py --check`;
   the local gate is authoritative. To go without it, generate (or update)
   with `--data include_ci=false`. It needs no secret: our packages come
   from the Gitea registry, keys are never in the repo. No `.github/`.
6. **Releases after that**: `antagor publish --bump patch|minor|major`
   (Human only, or the project's Architect) merges the accepted tickets,
   writes `CHANGELOG.md` from their titles, tags `vX.Y.Z` (semver, PEP 440)
   and runs `scripts/deploy.sh`, which pushes `main` with the tags to
   `origin` (Gitea). The gate (`release.py --check`) is a ticket check, so
   it has already passed. You never push by hand. Pick the part by SemVer
   (`architecture.md` §8: at `0.x` fixes and compatible features are
   patch, a breaking change is minor). There is no `version =` to edit,
   no `[Unreleased]` section and no fragment — one ticket per change.
   Other machines follow by `[tool.rb.install]`; you do not upgrade them.

## Non-negotiables (apply in both modes)

These are the parts of `reference/architecture.md` most likely to get
skipped under time pressure — check them explicitly:

- Every command has a human mode and a `--json` mode; agents must never be
  forced to parse decorated human output.
- Errors are raised as `CliError` subclasses with a stable `code`, and follow
  the exit-code table in `reference/conventions.md` — never a bare
  `sys.exit(1)` or an unstructured stack trace as the user-facing failure.
  Every command is wrapped in `@output.guard` (which is also what turns an
  unmapped exception into an `UNEXPECTED` JSON envelope); human errors go
  to stderr, stdout carries data only.
- A bare `<cli>` or `<cli> <group>` prints help and exits 0 — groups are
  made with `output.group(...)`; don't reintroduce `typer.Typer(...)` or
  `no_args_is_help=True` (Click exits 2 on that).
- External services are reached only through a `providers.HttpProvider`
  subclass (or a `providers/` module raising the same `ProviderError` /
  `AuthRequired`) — never `httpx`/`requests` calls sprinkled through
  `core/` or `commands/`. Each implements `health_check()`, and
  `auth status [--check] --json` keeps the exact §8 shape (a shape change
  is a breaking change); it never prints a credential value.
- No secret ever gets written to project-local config (`.{{package}}/config.toml`
  is safe to commit). Secrets only live in the OS keychain or env vars.
- `doctor` and the bundled `data/SKILL.md` are not optional extras —
  every generated/refactored CLI ships both. The SKILL.md stays
  conventions-only: never add a command list to it, the command's
  docstring is its documentation (that's what a bare `<cli>` renders).
- The quality gates are part of the package, not of CI alone:
  `fail_under` coverage in `pyproject.toml` (raise it, never lower it),
  ruff's `S` (security) rules, and the osv-scanner audit of `uv.lock`
  (a gate step when osv-scanner is installed; CI installs it). `uv run scripts/release.py --check` runs every gate locally
  and is what an agent runs before each commit. A refactored project gets all three.
- The package declares `[tool.rb.install]` and is installable (the wheel
  passes `release.py --check`) — see "Publish". A CLI that only runs
  from its own checkout hasn't met the "installed once, used from any
  project" premise in `reference/architecture.md`.
- **Changed a command's behaviour → update its docstring in the same
  commit**, then `uv run pytest --snapshot-update` and check the
  `tests/snapshots/help/` diff reads right. The docstring and `help=`
  strings are the `--help` text agents read. This is enforced, not
  advisory (`architecture.md` §5): the ticket check
  `scripts/check_command_docstrings.py` (Antagor runs it; the git hooks
  come from `antagor hooks install`), and blocking tests — each docstring has an
  `Example: {cli} <command> ...` line, each parameter a `help=`, each
  help page a snapshot. Don't bypass them: for a behaviour-neutral edit
  (a lint or type fix inside a command) keep the body AST-identical with
  `# noqa` / `# ty: ignore[...]` comments; never `SKIP_DOCSTRING_CHECK`
  (humans only). Every command is wrapped in `@output.guard` — the help
  contract test fails otherwise.
- Versions come only from git tags cut by `antagor publish`, the
  changelog only from ticket titles, dependencies on our other
  tools only by tag pin. SemVer is a promise about the CLI surface
  (flags, `--json` shape, exit/error codes) — `architecture.md` §8.
- Prefer `pathlib`/`shutil`/`platformdirs` over shelling out or hardcoded
  POSIX paths — the whole point is that it runs unmodified on macOS, Linux
  and Windows.

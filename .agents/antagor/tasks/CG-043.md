rb-release check verifies the Standard's mandatory rules from outside, on any package: it runs the console script it has just built and installed (the build + install wheel step) and probes it. Each failure names the step and the Standard section, so a package agent knows what to fix with no template tests. This fills the Standard-checks step that the gate move left as a passing placeholder.

Steps and the Standard sections they cite (the section names are fixed; standard.md uses the same):

| Step | Section | Rule |
|---|---|---|
| standard: commands | Commands | `<cli>` with no arguments lists the commands and exits 0; every command and group answers `--help` with exit 0 |
| standard: json | Output | every leaf command accepts `--json` (its help lists it) |
| standard: errors | Errors | an unknown option gives exit 2; with `--json` stdout is the error envelope (`ok: false`, `error.code`, `error.message`); every exit code seen is in the Standard's table |
| standard: health | Health | `doctor --json` and `auth status --json` exist, give the fixed envelope form (`auth status`: a `credentials` list, empty without keys) and an exit code from the table |
| standard: docs | Docs | the package has its README and AGENTS files (the .md names) |
| standard: ci | CI | a workflow under .gitea/workflows/ runs `rb-release check` |

## Acceptance

- Given a fixture package that meets every rule in the table, When rb-release check runs, Then every standard step prints ok and the gate ends with 'release: gate passed', exit 0 [check: sh scripts/check_template.sh]
- Given a fixture where one command has no --json, When the gate runs, Then it fails at 'standard: json', the message names the command and the section Output, exit 1 [check: sh scripts/check_template.sh]
- Given a fixture whose --json error is not the envelope (e.g. plain text on stdout), When the gate runs, Then it fails at 'standard: errors' naming section Errors; and given a fixture that exits 7 on bad input, Then the same step names the code 7 as outside the table [check: sh scripts/check_template.sh]
- Given fixtures without doctor, with auth status --json missing `credentials`, without a README file, without an AGENTS file, without a Gitea workflow, When the gate runs on each, Then it fails at the matching step (health, health, docs, docs, ci) naming its section [check: sh scripts/check_template.sh]
- Given a fixture whose bare command exits 2, When the gate runs, Then it fails at 'standard: commands' naming section Commands [check: sh scripts/check_template.sh]

## How to test

Integration: small fixture packages (one compliant; one per broken rule, each the compliant one with one change applied in the test) built and checked by the gate in tmp_path. Red first.

## Basis

The gate's existing steps (one method per step, the first failure stops and names the step); the envelope and exit codes of the template's conventions; the contract with sysadmin for doctor/auth status.

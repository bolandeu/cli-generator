The template's Antagor files lag behind current Antagor. The Human's rule: a package follows current Antagor whatever template version it is on. So the template holds only the package's own facts (its gate command, prefix, CI status URL) and never restates how Antagor works: Antagor's defaults and rules come from the installed Antagor. And this repo's CI checks the template against Antagor's current main, on every push and every night, so a new Antagor requirement turns it red at once. What Antagor expects now, from its owner:

1. The generated Antagor config:
   - `[publish]` gets `gate = "remote"` and `gate_status_url = "https://homeserver.tailee01ab.ts.net:3000/api/v1/repos/bolandeu/<repo>/commits/{commit}/status"`. `<repo>` is the last path segment of the `repository_url` answer when it is set, else the command name.
   - a top-level `heavy = ["rb-release check"]`.
   - `worker = "claude-code"` is dropped (Antagor's default).
   - Nothing else is added. In particular no `mode`, no daemon, hand-fix, floor or slow-run keys (the Human's, password-guarded), and no gate_command, timeouts or limits.
2. The generated AGENTS.md stays navigation only. It restates no Antagor rule: the hand-fix line goes; one pointer says the work process is Antagor's (its skill antagor-method).
3. The generated CODING_STANDARDS.md:
   - the TDD rule no longer says the red test is committed first and visible in git, since the worker does not commit. It says: every behaviour change comes with a test that fails without it, and the red run is in the worker's report.
   - the machine-local path `~/Work/dev/docs/testing.md` is removed.
   - the hand-fix line goes (an Antagor rule, not a judgement rule of this package).
4. This repo's template-gate CI installs antagor from its current main (no pinned commit) and also runs every night on a schedule, so the layout check of each rendered package runs against current Antagor even when this repo has no new commit.
5. The existing-package mode and its update part say, as the last step, that the Human runs `antagor -C <package root> remote-gate-accept` once per package (password). Until then the remote gate is not in force.

## Acceptance

- Given a package rendered with `repository_url=https://homeserver.tailee01ab.ts.net:3000/bolandeu/demo`, When its Antagor config is read, Then `[publish]` has `gate = "remote"` and the status URL for `bolandeu/demo`, `heavy` is `["rb-release check"]`, and there is no `worker`, `mode` or `gate_command` key; with a blank `repository_url` the URL names the command [check: sh scripts/check_template.sh]
- Given a rendered package, When `antagor layout check` runs in it with antagor's current main, Then it reports the layout complete [check: sh scripts/check_template.sh]
- Given the rendered CODING_STANDARDS.md and AGENTS.md, When they are read, Then no line says a test is committed before the code, no line names `~/Work/`, and neither file has a hand-fix line [check: sh scripts/check_template.sh]
- Given this repo's template-gate workflow, When its test reads it, Then the antagor install step names no commit or tag (current main), and the workflow has a nightly schedule trigger next to push [check: tests/test_repo_ci.py]

## How to test

The template's own tests that read the rendered Antagor config (the CI and scripts tests) get the new keys; the template gate script renders the variants and runs antagor's layout check; the repo test reads the workflow YAML.

## Basis

Follow the template's existing files and the copier answers; derive `<repo>` in the Jinja file, not in a new copier question. The generated docs stay in Russian, our skill docs in English, with no mention of our ADRs, plans, ticket or idea ids, or dates.

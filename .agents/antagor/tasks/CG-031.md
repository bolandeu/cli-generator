copier gets a bool question adopt_core (default false). With true the project depends on rb-cli-core>=0.1.2,<0.2 from the explicit gitea index, scripts/release.py is not generated, and a project updated from false to true loses its copy. With false nothing changes. The template gate renders both variants and an update round that flips the answer; the template's own tests of release.py run only where the script exists.

## Acceptance

- Given adopt_core=false, When a project is rendered, Then its file list and pyproject equal those rendered by the previous template release apart from the answers file [check: sh scripts/check_template.sh]
- Given adopt_core=true, When a project is rendered and synced, Then scripts/release.py is absent, uv.lock holds rb-cli-core from the gitea index, and uv run rb-release check passes [check: sh scripts/check_template.sh]
- Given a project generated with adopt_core=false and committed, When copier update --trust --defaults --data adopt_core=true runs, Then scripts/release.py is deleted and uv run rb-release check passes [check: sh scripts/check_template.sh]
- Given adopt_core=true, When the generated project's pytest runs, Then the tests of release.py are skipped with a reason naming rb-cli-core, not failed [check: template/tests/test_scripts.py]

## How to test

Integration via check_template.sh: a new adopt_core variant and an update round from false to true; rb-cli-core 0.1.2 is on the Gitea registry (network to homeserver needed, as for any registry dependency).

## Basis

copier templated _exclude (like include_auth) and, if copier update does not delete an excluded file on its own, a _migrations entry; the gitea index block CG-027 added to pyproject.

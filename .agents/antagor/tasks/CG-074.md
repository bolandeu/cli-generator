The Standard (Technology) lets a package translate its help and human messages for the whole CLI. The gate reads the command list only under the English heading (Typer's rich panel titled Commands, or Click's plain 'Commands:'), so a package that translated the panel title (serp: COMMANDS_PANEL_TITLE set to 'Команды') fails standard: commands and standard: health although it lists its commands. The gate must find the commands section by its shape, not by its English title: a section (rich panel or plain heading line) whose entries are command names, not options starting with '-'. English help keeps working exactly as now.

## Acceptance

- Given a demo CLI whose bare help titles the Typer rich commands panel 'Команды' and the options panel 'Параметры', When rb-release check runs, Then standard: commands and standard: health are ok and the commands step counts the same commands as with English titles [check: gate/standard/tests/test_standard.py]
- Given a demo CLI with Click plain help whose commands heading is translated ('Команды:'), When rb-release check runs, Then standard: commands is ok [check: gate/standard/tests/test_standard.py]
- Given a bare help that lists only options and no commands section at all, When rb-release check runs, Then it fails at standard: commands with 'lists no commands', also under the CI variables; the old test that renamed the heading to 'Verbs:' and expected a failure is rewritten to this case, since a renamed heading over command entries is now a valid translation [check: gate/standard/tests/test_standard.py]
- Given the options panel (entries starting with '-'), When the gate lists commands, Then no option is taken for a command, in English and in translated help [check: gate/standard/tests/test_standard.py]
- Given the template packages, When the template gate runs, Then it passes unchanged [check: sh scripts/check_template.sh]

## Feedback

### Attempt 1: the Architect's verdict

Regression found by comparing old vs new listed_commands on every help of real packages: spider 'urls --help' and 'sitemaps build --help' now list a phantom command 'crawl_id'. Their Options panel starts with a required option, rendered '*  --issue', so the next-panel-starts-with-'-' heuristic fails and the Arguments panel is read as commands. A failing help's 'Error' panel ('No such command ...') is also read as commands ('No'). The fix should not guess from panel order. Use the usage line instead: a help lists commands only when its 'Usage:' line has the COMMAND metavar (Typer and Click print it untranslated). In such a group help, the commands are the entries of every section whose entries are not options (an option entry starts with '-' after an optional '*' required marker). A help without COMMAND in its usage lists no commands. Add tests: an Arguments panel followed by an Options panel whose first entry is '*  --x'; a leaf with a translated Arguments panel; an Error panel; a group whose commands are split over two translated panels. Before you submit, compare the old and the new listed_commands on the real helps (every command of the template's minimal and all-parts packages, which check_template.sh renders); they must give the same lists for English help.

### Attempt 2: the Architect's verdict

Real-package comparison (old vs new listed_commands on every --help of serp, hostme, spider, wordstat, context, keys, bukvarix, gsc, dataio, clidocs, semkit): all equal except semkit 'read --help', where the new code adds the argument 'IN' as a command. Its usage is 'Usage: semkit read [OPTIONS] [IN] COMMAND [ARGS]...': a group with its own argument, so its help has an Arguments panel and command panels. Rule to add: an entry whose name appears as a metavar in the help's Usage line (case-insensitive, brackets stripped, e.g. IN, crawl_id) is an argument, never a command; commands never appear in the usage line. Add a test for a group with an argument (usage '[OPTIONS] [IN] COMMAND [ARGS]...', Arguments panel 'Аргументы' with 'in', commands panel 'Команды'). Keep every earlier case green.

## Problem

Today both exist: the template renders .gitea/workflows/ci.yml that repeats rb-release check on the Gitea runner, and the Standard's CI section makes that workflow Mandatory, while the publish gate already runs locally ([publish] gate = local). The Human, 2026-10-29 and again 2026-11-08: CI is either remote or local, not both — and it is local. Half-done already: cli-generator's own antagor.toml moved to the local gate, but template-gate.yml, tests/test_repo_ci.py and the template workflow are still here.

## Goal

A generated package has exactly one gate — rb-release check on the machine that builds it. No .gitea/workflows/ci.yml in a new package, none in an updated one, the Standard says so, and Gitea keeps releases only.

## Acceptance (Given–When–Then)

- Given a package generated from the template, when its tree is read, then it has no .gitea/workflows/ci.yml and no answer turns one on
- Given an existing package, when copier update runs to the new tag, then its old .gitea/workflows/ci.yml is gone and the gate line in its AGENTS.md names rb-release check locally
- Given the Standard, when the CI section is read, then it states the local gate as the only gate and names no Gitea workflow

## Implementation decisions

- The local gate is the only gate; the release pushes main with tags after it is green, and Gitea stores releases.

## Test seams

- the generated package tree and scripts/check_template.sh

## Out of scope

- rolling the removal out in each of the 21 packages: their agents take it with copier update
- turning the Gitea runners off (sysadmin)

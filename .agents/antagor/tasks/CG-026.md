A generated package gets one CI workflow that Gitea Actions runs: runner label docker, the shared ci-cache volume, uv bootstrapped into the cache, then release.py --check. The GitHub workflow and the private_deps GitHub-token path are gone. include_ci=false still generates no workflow.

## Acceptance

- Given a project rendered with include_ci=true, When its files are listed, Then .gitea/workflows/ci.yml exists with runs-on docker, a ci-cache volume, fetch-depth 0 and the step uv run scripts/release.py --check, and no .github directory exists [check: sh scripts/check_template.sh]
- Given a project rendered with include_ci=false, When its files are listed, Then no .gitea or .github workflow exists [check: sh scripts/check_template.sh]
- Given copier.yml, When it is read, Then private_deps is gone or no longer produces a GitHub token step, and every uses: tag in the workflow exists upstream [check: sh scripts/check_template.sh]

## How to test

Integration: a test inside the generated project (template/tests/test_ci.py, a plain .py) reads its own .gitea/workflows/ci.yml when present; check_template.sh renders all variants and runs it. AGENTS.md's uses:-tag loop is pointed at the new file.

## Basis

Follow semkit's .gitea/workflows/ci.yml (/Users/bolandau/Work/tools/semkit/.gitea/workflows/ci.yml): container node:22-bookworm, volume ci-cache:/cache, UV_CACHE_DIR/UV_PYTHON_INSTALL_DIR in /cache, uv installed into /cache/bin. Keep the lowest-supported-Python logic of the current GitHub workflow if it fits.

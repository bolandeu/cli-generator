Antagor refuses a task that touches a module without a module docstring, and most modules a package gets from the template have none, so every package's first task on them pays for it. The help of init also names the wrong folder: it says the command's name, while the folder is named by the package.

1. Every Python module the template renders, in every optional part and in the tests, starts with a module docstring: what is in the file and why, in one paragraph. Modules that already have one keep it.
2. The template gate script checks that every Python module of each rendered variant has a module docstring, and names the modules that do not.
3. The help of init names the folder it creates by the package's name (`.<package>/config.toml`), which differs from the command's name when they differ.
4. copier update from the previous release tag still adds no conflict to a package that did not change those modules.

## Acceptance

- Given a package rendered with every optional part and one with none, When the template gate script runs, Then every Python module of each has a module docstring [check: sh scripts/check_template.sh]
- Given a package with package_name rb_sitemap_xml and cli_name sitemap-xml, When init --help runs, Then the help names .rb_sitemap_xml/config.toml [check: template/tests/test_cli.py.jinja]
- Given a package made from the previous release tag, When copier update runs to this template, Then no conflict appears and the package's tests pass [check: sh scripts/check_template.sh]

## How to test

The template gate script renders the variants and checks each module's docstring with Python's own parser; a CLI test reads init's help in a package whose command and package names differ.

## Basis

Follow the module docstrings the template already has (output.human, scripts) and the {cli} substitution output.guard does for command help. No new tool, script or dependency.

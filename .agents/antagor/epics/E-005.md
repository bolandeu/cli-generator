## Problem

The requirements for a package are spread over three reference files (~1100 lines) mixed with history and template detail; many mandatory rules are checked only by tests that template-made packages carry, so a package not made from the template cannot be checked; bringing a package to the standard means a copier update with conflicts. The gate itself lives in a separate repo (cli-core) with its own versions and registry package.

## Goal

One short English Standard (skills/cli-builder/reference/standard.md) with every rule marked mandatory or recommended. rb-release check verifies every mandatory rule from outside, on any package, and names the rule it fails. The gate's code lives in this repo (gate/); a package runs it with one uvx command pinned to the template tag, as a development tool only. cli-core is gone: repo, project, folder and registry package.

## Acceptance (Given–When–Then)

- Given the Standard, When it is read, Then every rule is marked mandatory or recommended, sections are named (no §N), and every mandatory rule names the gate step that checks it
- Given a fixture package that meets every mandatory rule, When rb-release check runs, Then it ends with 'release: gate passed' and exit 0
- Given fixture packages that each break one mandatory rule (a command without --json, a wrong error envelope, an exit code outside the table, doctor --json or auth status --json of the wrong form, no README.md / AGENTS.md / CI workflow, no [tool.rb.install]), When rb-release check runs, Then it fails at a named step whose message names the Standard's section, exit non-zero
- Given any package (made from the template or not), When 'uvx --from git+<gitea>/bolandeu/cli-generator.git@<tag>#subdirectory=gate rb-release check' runs in it, Then the gate runs with no dependency added to the package and nothing of it is needed at run time
- Given the gate moved from cli-core, When its existing tests and the parity cases run in gate/, Then they pass: same step names, last line and exit codes as rb-cli-core 0.1.x
- Given a project generated from this template, When its files are read, Then it has no scripts/release.py and no adopt_core question; CI, antagor.toml, AGENTS.md and README call the uvx command pinned to the template tag; AGENTS.md links to the Standard by its Gitea URL; and the template gate passes for every variant
- Given semkit moved to this template version, When cli-core is retired, Then the Gitea repo bolandeu/cli-core and the registry package rb-cli-core are deleted, the Antagor project and /Users/bolandau/Work/tools/cli-core are removed, and no file of this repo or of the template names cli-core or rb-cli-core [check: manual]

## Implementation decisions

- gate/: a Python package in this repo (distribution and command rb-release), the code and tests moved from cli-core; runs over the package in the cwd
- Standard checks: a gate step family that runs the package's installed console script (after build + install wheel) and checks the mandatory rules from outside; each failure names the Standard section
- Template: the gate is not copied and not a dependency; CI, antagor.toml and docs run it through uvx from this repo at the tag in .copier-answers.yml
- standard.md replaces architecture.md, conventions.md and help-standard.md; the refactor checklist moves into the skill later (plan step 3)

## Test seams

- rb-release check on fixture packages: one compliant, one per broken mandatory rule; step name, message and exit code
- sh scripts/check_template.sh: every generated variant passes the new gate

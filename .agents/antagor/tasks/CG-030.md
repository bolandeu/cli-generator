The Gitea CI workflow installs osv-scanner and gitleaks into the shared cache (like uv) before release.py --check, so in CI the vulnerability audit and the secret scan run instead of being skipped with a notice. A tool already in the cache is not downloaded again.

## Acceptance

- Given the rendered .gitea/workflows/ci.yml, When it is read, Then a step before release.py --check puts osv-scanner and gitleaks into /cache/bin at pinned versions, skipping the download when the binary is there [check: sh scripts/check_template.sh]
- Given the workflow, When its downloads are read, Then each URL names an exact release version that exists upstream (no latest) [check: sh scripts/check_template.sh]

## How to test

Integration: template/tests/test_ci.py reads the workflow; check_template.sh renders it. Check release URLs exist with gh api once while writing.

## Basis

The uv bootstrap step of the same workflow; gitleaks and osv-scanner linux x64 release assets on GitHub.

## Read first

- `template/.gitea/workflows/ci.yml`
- `scripts/check_template.sh`

## Out of scope

- release.py, the skill, other workflow behaviour

## Feedback

### Attempt 1: the Architect's verdict

One fix: the cache check is by name only ([ -x /cache/bin/gitleaks ]), so when a later template release bumps the pinned version, every runner keeps the old binary from the shared ci-cache forever. Cache per version, e.g. /cache/bin/gitleaks-8.30.1 and /cache/bin/osv-scanner-2.7.0, and put them on PATH under their plain names (symlink in a per-job dir or in /cache/bin pointing to the versioned file). Add a test that the cached path contains the pinned version. URLs are fine (both return 200).

### Answer to finding #1

> check_template.sh update-round fails on this machine (gitleaks installed): the previous release tag's tests/test_auth.py line 21 lacks '# gitleaks:allow', so release.py --check in the updated project finds a 'secret' in history. Not caused by CG-030; auto-clears once a release tag includes the allow comment, or the update-round needs a gitleaks allowlist.

Fixed by CG-029: template .gitleaks.toml allowlist of the fake test values

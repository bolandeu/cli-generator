## Problem

Keeping a package on the Standard costs more than it should. The gate command with its template tag is written into several package files, and the line in Antagor's checks conflicts on every copier update in a package that follows Antagor's advice for mode fast. Bringing an old package onto the Standard takes many gate runs, because the gate stops at the first red step. Antagor refuses a task that touches a module without a module docstring, and most template modules have none, so every package pays for it.

## Goal

A template update touches the gate tag in one package file and never conflicts on it; one gate run shows every red step; every module a package gets from the template has a module docstring. Every change makes the template, its upkeep, its updates or its use by packages simpler; none adds a new part.

## Acceptance (Given–When–Then)

- Given a package rendered from the template, When its files are read, Then the gate command with the template tag is written only in its CI workflow, the agents file, the coding standards and the readme point to that line, and Antagor's checks hold no gate command
- Given a package made from the previous release tag, with the gate command in Antagor's checks or with fast-mode checks without it, When copier update runs to this template, Then no conflict appears, the gate command is gone from the checks, and the package's tests pass
- Given a package with two failing gate steps, When rb-release check --keep-going runs, Then it runs every step, lists both failed steps at the end, marks a step that needs a failed step's output as skipped, and exits 1 (3 when only the dependency audit failed)
- Given the same package, When rb-release check runs without the flag, Then it stops at the first failed step with the same output and exit code as before
- Given a package rendered with every optional part and with none, When the template gate script runs, Then every Python module of the package has a module docstring, and init's help names the package's own folder
- Given the Standard, When its Release section is read, Then it describes the remote gate that runs before the tag

## Implementation decisions

- Template answers: the gate command stays one rendered value; the CI workflow is the only file that writes it; Antagor's config keeps only the docstring check in checks, the remote gate and heavy
- Package docs (agents file, coding standards, readme) name the gate as the rb-release check line of the CI workflow, not as a copy of the command
- Gate: rb-release check gets a --keep-going option; the step runner collects failures instead of returning at the first; a step declares which earlier step it needs, to be skipped when that one failed
- Template modules: a module docstring in each; the template gate script checks every rendered module; the help of init takes the package's folder name
- Standard, Release: the remote gate before the tag replaces the line that says no full gate runs before the tag

## Test seams

- The rendered package: copier copy and copier update from the previous release tag, then the package's own test suite (the template gate script)
- The rb-release check command (the gate's tests)

## Out of scope

- A new tool, script, command or dependency: the work changes only the template, the existing gate and the existing template gate script
- A new optional part, question or file in the template
- Antagor's own settings (timeouts, mode, worker) in the template
- The other items of the freeze list (the Python 3.11 fixture, the gate timeout)
- Changes in the packages' own repositories: they come through copier update

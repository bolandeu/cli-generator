Bringing an old package onto the Standard takes many gate runs: the gate stops at the first failed step, so each run shows one problem. A package probe took 7 runs.

1. `rb-release check --keep-going` runs every step. After the last step it prints the list of failed steps and the verdict line. A step that needs the output of a failed step (for example installing a wheel whose build failed) is not run and is listed as skipped.
2. The exit code with the flag: 1 when any code step failed, 3 when only the dependency audit failed, 0 when all passed.
3. Without the flag the gate is unchanged: it stops at the first failed step with the same output and exit code.
4. The command's help names the flag and when to use it (the first run on an old package).

## Acceptance

- Given a package with two failing code steps, When rb-release check --keep-going runs, Then every step runs, both failed steps are listed at the end, and the exit code is 1 [check: gate/tests/test_release.py]
- Given a package whose build step fails, When rb-release check --keep-going runs, Then the steps that need the built wheel are listed as skipped, not as failed [check: gate/tests/test_release.py]
- Given a package where only the dependency audit fails, When rb-release check --keep-going runs, Then the exit code is 3 [check: gate/tests/test_release.py]
- Given a package with a failing step, When rb-release check runs without the flag, Then it stops at that step with the same output and exit code as before [check: gate/tests/test_release.py]

## How to test

Unit level through the gate's step runner and the Typer command, with fake steps that pass, fail or need another step; no real package build.

## Basis

Follow the existing step runner and its output lines (release: <step> ... ok / FAILED, the verdict line). No new command, script or dependency.

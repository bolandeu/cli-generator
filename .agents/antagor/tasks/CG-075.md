The update instructions for an existing package say that when an option changes, copier deletes the files the new answers no longer generate "except files the package edited". That is wrong: in hostme, `include_project=false` deleted the package's heavily edited business-logic module, and the package restored it from git. Batches 2–3 also showed three more gaps that cost each package a round. The Standard allows only an exact fake value in the gitleaks config, so a package with a revoked real key in its history has no allowed way to pass the secret scan. Packages used a fingerprint-only `.gitleaksignore` line, which the owner accepted.

## Acceptance

- Given the section "Changing an option" of the update instructions, When a reader follows it, Then it says copier may delete a file the package edited, and tells them to run `git status` and restore every deleted package file from HEAD (`git checkout HEAD -- <file>`) before the gate [check: sh scripts/check_template.sh]
- Given the step "Clean tree", When a reader follows it, Then it says untracked files count too and names `git stash -u` before the update and `git stash pop` after its commit [check: sh scripts/check_template.sh]
- Given the step "Conflicts", When a reader follows it, Then it warns that a hunk next to a reworded template comment can carry a package block (e.g. `[[tool.rb.external]]`), and tells them to read the diff of the package's pyproject line by line [check: sh scripts/check_template.sh]
- Given the Standard's rule on the secret scan (section Credentials) and the instructions' "Secret scan", When a real key was leaked in history and the Human revoked it, Then both allow exactly one fingerprint line per finding in `.gitleaksignore` (`<commit>:<file>:<rule>:<line>`, no value), and still forbid a path, a rule disable or the key's value [check: sh scripts/check_template.sh]

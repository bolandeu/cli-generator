## Problem

The contract with sysadmin (docs/contracts/sysadmin.md, accepted 2026-10-19) says how packages are built, installed, keyed and kept current. The template and the skill still contradict it: CI sits in .github/workflows and never runs in Gitea; nothing stops a secret before push; our packages pin each other by git tag, which Renovate and tool-updater do not follow; the template source and repository_url point at GitHub; the standard names a tools-watch that does not exist; nobody can see which package lags behind the template.

## Goal

A package generated or updated from the new template release has a green CI in Gitea, a gate that refuses a committed secret, dependencies on our packages through the Gitea registry, Gitea URLs in its copier answers, and a template update that runs without questions or keys. The skill's Update mode tells a package agent every step. A report shows which packages lag behind the latest template tag.

## Acceptance (Given–When–Then)

- Given a project generated from the working tree, When it is rendered, Then .gitea/workflows/ci.yml exists for runner label docker and runs release.py --check, and no .github/workflows file is generated
- Given a generated project with a committed fake secret, When release.py --check runs with gitleaks installed, Then it fails at a named secret step and exits 1
- Given gitleaks is not installed, When release.py --check runs, Then the secret step is skipped with a notice and the gate result does not change
- Given a generated project, When a .env file is created, Then git status stays clean
- Given a generated project that depends on one of our packages, When the dependency is declared as the standard says, Then uv resolves it only from the Gitea index (explicit) and release.py --check passes; a package of the same name on PyPI is never installed
- Given a project generated by the skill's instructions, When .copier-answers.yml is read, Then _src_path is the Gitea URL of cli-generator and repository_url defaults to the Gitea repo
- Given a generated project, When copier update --trust --defaults runs non-interactively with no keys in env or keychain, Then it finishes and the gate passes
- Given an existing package on an older template, When its agent follows the skill's Update mode, Then the steps cover the CI move (old .github workflow removed), gitleaks, the registry dependency form, the Gitea _src_path, and shared key names via legacy_env
- Given the drift report runs, When Gitea lists repos with .copier-answers.yml, Then it prints per repo the template version and whether it lags the latest tag, with --json; a repo without answers is listed as not from the template; Gitea unreachable gives a named error and a non-zero exit
- Given the standard is read, When it is searched for tools-watch, Then there is no match, and §4 links the key rules of the contract (Doppler tools/prd, name = env name, legacy_env for a shared key)

## Implementation decisions

- Template CI: one Gitea Actions workflow, shape of semkit's (container with ci-cache, uv bootstrap, release.py --check); the GitHub workflow and the private_deps GitHub token path go away
- Gate: a secret-scan step in release.py --check with gitleaks over the git history, skipped with a notice when not on PATH; exit code 1 on findings; template .gitignore covers .env*
- Standard §8: dependency on our package = version range + [[tool.uv.index]] Gitea PyPI with explicit = true + source by index; the gate's 'installed from a package index instead of git source' guard is replaced by an equivalent guard for the explicit index
- Skill: template source and default repository_url are Gitea URLs; Update mode gets the migration steps for this epic
- Standard §4: key rules link to the contract; a shared key without CLI prefix is read through the provider's existing legacy_env; no code change in credentials
- Drift report: a script in this repo that reads Gitea's API (anonymous read) and the latest template tag

## Test seams

- sh scripts/check_template.sh (rendered project + full gate)
- release.py --check output and exit code in a generated project
- drift report CLI --json output (tests with a faked Gitea API)

## Out of scope

- The shared library rb-cli-core (IDEA-254, own clarification)
- Infra parts of the contract: Renovate config, Mac doppler run wrapper, key renames in Doppler, Mac/homeserver version check (sysadmin)
- Running copier update in existing packages: their agents do it on the Human's command
- Changing credentials code or the auth status shape
